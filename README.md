# Seoul Estate AI Prototype

서울 아파트 실거래, 신고가, 토지거래허가구역, 온디바이스 검색비서를 한 화면에서 확인하는 정적 MVP입니다.

## 실행

`index.html`을 브라우저로 열면 바로 실행됩니다. 로컬 서버를 쓰려면 아래처럼 실행할 수 있습니다.

```bash
python3 -m http.server 5173
```

## 현재 범위

- 서울 실거래 샘플 데이터 기반 검색
- 자연어 조건 추출
- 신고가 판정
- 토지거래허가 일자별 내역과 단지 상세
- 아가리 호가, 부동산 캘린더, 청약 공고, 고시/공고, 손피 계산기형 홈 서비스 구성
- 갈아타기 후보 단지별 국토교통부 실거래 API 매칭
- AppFolio 스타일을 참고한 화이트/스카이 블루 카드 UI

## 다음 단계

- 서울 열린데이터광장 API 수집 배치
- DuckDB-Wasm 또는 SQLite-Wasm 로컬 저장소
- WebLLM/Transformers.js 기반 브라우저 내 LLM 검색비서
- 구/동/단지별 실거래 Parquet 데이터 다운로드

## API

- `GET /api/transactions`: 서울 25개 구 최근 실거래
- `GET /api/candidate-transactions?months=12`: 갈아타기 후보 단지 실거래 매칭
  - `.env`에 `KAPT_API_KEY`가 있으면 공동주택 관리정보와 건축물대장 정보를 추가 보강합니다.
  - 응답의 `kapt` 필드에서 `codeMatched`, `enriched`, `missingCode`, `failed`로 누락 여부를 확인할 수 있습니다.
  - `refresh=1`을 붙이면 서버 캐시를 우회해 다시 수집합니다.
- `GET /api/regime-search?district=&q=`: 정권별 비교 — 단지 검색 (아래 정권별 비교 섹션 참고)
- `GET /api/regime-complex?id=`: 정권별 비교 — 단지 상세(연도별 시계열 + 정권 구간 상승률)

## 정권별 아파트 상승률 비교 (`regime.html`)

문재인·윤석열·이재명 정부 구간별로 아파트 실거래가 상승률을 비교하는 별도 대시보드입니다.

### ★ 데이터 원칙

- **수집된 실거래 데이터만 표시합니다.** 샘플·더미·추정 값은 어디에도 넣지 않습니다.
- 특정 연도에 거래가 없거나 아직 수집되지 않았으면 값은 `null`로 두고 화면에 "데이터 없음" / "산출 불가"로 명확히 표기합니다.
- API 호출이 실패하면 해당 지역·월은 "수집 실패"로 남고, 스크립트를 다시 실행하면 실패한 부분만 재시도됩니다. 실패를 이유로 값을 지어내지 않습니다.
- 거래 3건 미만인 연도는 값은 그대로 보여주되 "표본 부족" 경고를 함께 표시합니다(값을 숨기지 않습니다).

### 1. 국토교통부 실거래가 API 키 발급

1. [공공데이터포털](https://www.data.go.kr)에서 **"국토교통부_아파트 매매 실거래자료"** 검색
2. 활용신청(무료) → 승인 후 마이페이지에서 **"일반 인증키(Decoding)"** 복사
3. 프로젝트 루트 `.env` 파일에 추가 (기존 `MOLIT_API_KEY`와 동일한 키를 그대로 씁니다):
   ```
   MOLIT_API_KEY=발급받은_디코딩_키
   ```

### 2. 실거래 수집 (로컬에서 실행 — 시간이 걸립니다)

```bash
# 서울 25개구 × 2016.01~현재 전체 수집 (기본값)
npm run collect:regime

# 특정 지역·기간만 수집하고 싶을 때
node scripts/collect-regime-transactions.mjs --districts=강남구,서초구 --from=202001 --to=202512

# 이미 실패했던 지역·월만 재시도됩니다 (성공분은 캐시로 스킵). 강제로 전부 다시 받으려면:
node scripts/collect-regime-transactions.mjs --force
```

원본 응답은 `data/cache/{법정동코드}/{YYYYMM}.json` 에 캐시됩니다(용량이 커서 git에는 커밋하지 않습니다).

### 3. 대시보드용 인덱스 생성

```bash
npm run build:regime-index
```

`data/cache/` 를 집계해 `data/regime-index.json` 을 만듭니다. 이 파일이 `regime.html`의 검색·비교 기능이 읽는 유일한 데이터 소스입니다. 수집을 더 진행한 뒤에는 이 명령을 다시 실행해 인덱스를 갱신하세요.

### 4. 대시보드 열기

`npm start` 로 서버를 띄운 뒤 `/regime.html` 로 접속하면 [검색] 탭에서 단지를 찾아 [비교하기] 탭에 담고, 정권별 상승률·연도별 추이·기준 단지 대비 상대 지수를 확인할 수 있습니다. 비교 목록은 브라우저 `localStorage`에 저장되어 새로고침해도 유지됩니다.

수집 전에는 "아직 수집된 데이터가 없습니다" 상태로 안전하게 표시되며, 검색이나 프리셋 불러오기를 눌러도 실제 데이터가 없는 단지는 절대 추가되지 않고 그 사실이 그대로 안내됩니다.

### 5. 매일 자동 갱신 (서버가 알아서 함)

별도로 크론을 설정할 필요가 없습니다. `npm start`로 띄운 `server.js`가 **켜져 있는 동안** 내부적으로 매일 아침 6시(서버 시간 기준)에 스스로 갱신합니다.

| 순서 | 하는 일 |
| --- | --- |
| 1 | 아직 못 받은 지역·월을 수집 (이미 받은 건 건너뜀) |
| 2 | **최근 3개월은 강제로 다시 수집** — 실거래 신고는 계약 후 최대 30일까지 늦게 올라오고, 취소 건도 뒤늦게 반영되기 때문 |
| 3 | `data/regime-index.json` 재생성 |
| 4 | 결과 점검 — 단지 0개거나 지역이 통째로 빠졌으면 **파일을 덮어쓰지 않고 어제 데이터를 그대로 유지** |

서버가 처음 켜질 때(또는 오늘 아직 한 번도 갱신 안 했으면) 바로 한 번 실행되고, 그 다음부터는 매일 6시에 자동으로 돕니다. 서버 콘솔에 `[regime]`으로 시작하는 로그로 진행 상황이 찍힙니다.

> **주의:** 이 서버(`server.js`)는 Vercel에는 올라가지 않습니다(`.vercelignore` 참고 — Vercel은 파일을 저장할 수 없는 서버리스라 자동 갱신을 못 돌립니다). 자동 갱신이 실제로 동작하려면 이 서버를 **계속 켜져 있는 곳**(Fly.io 같은 상시 서버 호스팅, 또는 내 컴퓨터를 계속 켜두기)에 올려둬야 합니다.

### Fly.io 배포

`Dockerfile` · `fly.toml` · `.dockerignore` 가 이미 준비돼 있습니다. Fly.io는 컨테이너가 **계속 떠 있고**, **디스크에 파일을 남길 수 있는**(Volume) 서비스라 이 서버 구조에 잘 맞습니다 — 매일 자동 갱신도, `data/` 캐시가 재배포 후에도 남는 것도 여기서 그대로 동작합니다.

아래는 [Fly.io](https://fly.io) 계정으로 직접 실행해야 하는 단계입니다(계정 로그인이 필요해 대신 실행해 드릴 수 없어요):

```bash
# 1) Fly CLI 설치 (최초 1회)
curl -L https://fly.io/install.sh | sh

# 2) 로그인
fly auth login

# 3) 앱 등록 — fly.toml 이 이미 있으므로 새로 만들지 말고 그대로 사용
#    (app 이름이 이미 쓰이고 있다면 fly.toml의 app = "..." 값을 바꾸세요)
fly launch --no-deploy

# 4) 데이터 보존용 디스크 생성 (fly.toml의 [mounts] 와 이름을 맞춰야 함: regime_data)
#    사이즈는 25개구 × 10년 전체 수집을 고려해 3GB 권장 (나중에 fly volumes extend 로 늘릴 수 있음)
fly volumes create regime_data --region nrt --size 3

# 5) 비밀키 등록 (.env 파일을 올리는 게 아니라 Fly 서버에 직접 암호화 저장됨)
fly secrets set MOLIT_API_KEY=발급받은_디코딩_키
fly secrets set KAPT_API_KEY=발급받은_K-apt_디코딩_키

# 6) 배포
fly deploy

# 7) 로그로 자동 갱신 진행 확인 ([regime] 으로 시작하는 줄)
fly logs
```

배포되면 `https://<앱이름>.fly.dev` 로 접속됩니다. `REGIME_AUTO_PUSH`는 켜지 않아도 됩니다 — 이 서버 자체가 서비스 주소가 되므로 깃허브·Vercel로 되돌려 보낼 필요가 없어요(Vercel을 별도로 병행 운영할 계획이면 그때 켜세요).

**처음 배포하면 데이터가 비어 있습니다.** 지금 로컬에서 이미 모아둔 `data/cache/`·`data/regime-index.json`은 이미지에 포함되지 않으므로(용량 문제로 `.dockerignore` 처리), 서버가 뜨자마자 스스로 처음부터 수집을 시작합니다(1~5절 참고). 서울 25개구 전체를 처음부터 받으려면 시간이 꽤 걸리니, 급하면 지역을 좁혀 로컬에서 먼저 채워둔 뒤 `fly sftp shell`로 볼륨에 복사하는 방법도 있습니다 — 필요하면 알려주세요.

#### 지금 이 서버 주소를 그대로 서비스로 쓴다면

여기까지가 전부입니다. 서버가 갖고 있는 `data/regime-index.json`이 곧 서비스 데이터라서, 매일 갱신되면 바로 반영됩니다.

#### 나중에 Vercel 주소로 서비스한다면

Vercel은 깃허브에 새 커밋이 올라올 때만 재배포됩니다. 즉, 이 서버가 아무리 매일 갱신해도 그 결과를 깃허브에 올려주지 않으면 Vercel 화면은 그대로예요. `.env`에 아래 한 줄을 추가하면, 갱신될 때마다 `data/regime-index.json`을 자동으로 커밋·푸시해서 Vercel이 따라가게 만듭니다.

```
REGIME_AUTO_PUSH=1
```

이 서버를 띄운 컴퓨터에 이 저장소로 `git push`가 가능한 권한(로그인)이 미리 되어 있어야 합니다. 켜두지 않으면(기본값) 로컬 파일만 갱신되고 깃허브·Vercel에는 반영되지 않습니다.

인덱스를 지금 바로 한 번 갱신하고 싶다면 수동으로도 실행할 수 있습니다:

```bash
npm run update:regime    # 수집 + 인덱스 생성 + 점검을 한 번에
```
